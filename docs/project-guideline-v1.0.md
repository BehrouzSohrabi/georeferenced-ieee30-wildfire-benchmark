# Georeferenced IEEE 30-Bus Wildfire Benchmark: Dataset and Data Descriptor Guideline

*Version 1.0 · 11 October 2026 · Working guideline for the research team*

## 1. Purpose and definition of done

Turn the georeferenced IEEE 30-bus system and wildfire scenario pipeline from Sohrabi et al. (IEEE Access, 2024, DOI 10.1109/ACCESS.2024.3439724) into a citable, reproducible public dataset with a peer-reviewed data descriptor.

**Positioning.** A small, standard, synthetic benchmark (no critical-infrastructure restrictions) for wildfire–grid co-simulation. It bundles network geometry, landscape and weather inputs, ignition scenarios, FARSITE outputs, ACOPF results and metrics. It complements, and does not replace, larger geographically accurate systems such as CATS and RTS-GMLC.

**The project is done when all of these hold:**

- Dataset v1.0.0 is deposited with a DOI, together with a clean public code repository.
- Every number in the manuscript can be regenerated from released data by script.
- A person outside the build team reproduces the core results using only the documentation.
- The data descriptor is submitted and every phase gate is signed off.

## 2. Ground rules (apply to all phases)

- **Scripted provenance.** No manual edits to data or numbers. Every manuscript table and figure is generated by a script in the repository.
- **Coordinates and units.** Store in WGS84 (EPSG:4326). Compute lengths and areas in California Albers (EPSG:3310). Use SI units and state MW, MVAr, MVA and p.u. explicitly.
- **Open formats.** GeoJSON or GeoPackage, CSV or Parquet, MATPOWER .m, GeoTIFF. Keep native FARSITE formats alongside open equivalents.
- **Stable IDs.** Zero-padded IDs (bus\_01, branch\_01, ign\_0001, scen\_0001) are never reused or renumbered across versions.
- **Discrepancy log.** Any difference from the IEEE Access results goes in docs/discrepancies.md with cause and resolution. A difference is a finding, not a failure.
- **Decision log.** Every design decision is recorded in docs/decisions.md with date, owner and rationale.
- **Gates.** Each phase ends with a gate review by someone who did not do the work. Waiving a pass criterion requires written PI approval and a stated reason.
- **Scope freeze.** Scope is frozen at the Phase 0 gate. New ideas go to a v1.1 backlog.

## 3. Roles

- **Project lead (PI):** owns decisions, approves waivers, signs gates.
- **Grid modeling lead:** Phases 1 and 4.
- **Fire modeling lead:** Phases 2, 3 and 5, with input from the fire-science co-author.
- **Data steward:** Phases 3 and 6 (repository, manifest, checksums, DOI).
- **Writer / corresponding author:** Phase 7 and submission.
- **Independent verifier:** gate reviews and the Phase 8 cold-start reproduction. Must not have built any part of the dataset.

One person may hold several roles, except the independent verifier.

## Phase 0 — Scoping, audit and decisions

**Objective:** establish exactly what exists, what may be released, and what the paper will claim.

**Tasks**

- Inventory every file in the GitHub repo and in lab storage, with provenance, version, size and license.
- Choose the exact IEEE 30-bus case variant (MATPOWER case30 or the ICSEG version) and record why.
- Build a related-work comparison covering CATS, RTS-GMLC, synthetic geolocated grids, and ad hoc geographic placements of the IEEE 30-bus system in other wildfire papers.
- Check rights and compliance: funder data-sharing terms (USDA grant 22-CS-11221636-121), co-author and institutional approvals (University of Denver, Quanta Technology, Pyrologix), upstream licenses (LANDFIRE, NREL NSRDB, FARSITE, ICSEG or MATPOWER), and reuse of figures from the CC BY-NC-ND 4.0 IEEE Access paper.
- Shortlist venues and capture each one's current data-descriptor requirements.

**Deliverables**

- D0.1 Asset inventory (CSV).
- D0.2 Decision record: case variant, CRS, data license, code license, repository and DOI provider, target venue, ID scheme.
- D0.3 Related-work matrix (columns: scale, real or synthetic, coordinates, line geometry, scenarios, outputs, license).
- D0.4 Rights and compliance memo.
- D0.5 Authorship and contribution list (CRediT), plus venue requirements checklist.

**Pass criteria**

- P0.1 Every file to be released has a known provenance and a license compatible with the chosen data license.
- P0.2 The decision record is signed by the PI.
- P0.3 The matrix includes at least 4 comparators and states at least 3 concrete differentiators.
- P0.4 Funder terms and co-author or institutional approvals are documented in writing.
- P0.5 The venue checklist covers data availability, validation section, file formats and size limits.

## Phase 1 — Network layer curation

**Objective:** produce a correct, fully documented georeferenced network.

**Tasks**

- Freeze the case file and document any change from the upstream reference.
- Build the branch table: 41 branches, of which 34 are lines and 7 are links (transformer-type branches). Label type explicitly. The IEEE Access tables omit link rows without saying so.
- Document how bus coordinates and line polylines were produced and why those corridors were chosen.
- Explain geographic treatment of links and of co-located nodes. Node groups {10, 13, 14, 15}, {2, 3, 8, 16} and {6, 28} have identical susceptibility values in the paper, and this must be explained.
- Compute lengths in EPSG:3310.
- State the electrical-parameter policy. Variant A keeps standard impedances (topology-only mapping). Optional variant B scales reactance with line length.

**Deliverables**

- D1.1 Case file (.m) and a diff against the upstream reference.
- D1.2 buses file (GeoJSON and CSV) with bus\_id, lon, lat, type, demand and generation.
- D1.3 branches file (GeoJSON polylines plus CSV) with from, to, rating\_mva, type (line or link), length\_km.
- D1.4 Network map and topology figure.
- D1.5 Network section of the data dictionary.
- D1.6 Optional variant B with documented scaling.

**Pass criteria**

- P1.1 Branch count is 41 (34 lines plus 7 links) and every branch maps to the correct from and to buses.
- P1.2 All buses and lines lie within the study box (37.6–38.1 N, 120.7–120.0 W), and every line endpoint is within 1 m of its bus coordinate.
- P1.3 Total line length reproduces the paper's 702 km within 0.5%, or the difference is explained.
- P1.4 Base-case ACOPF converges and matches the reference objective of the chosen case within 0.1%, or all modifications are listed.
- P1.5 The identical-susceptibility node groups are explained in the discrepancy log.
- P1.6 Files load without error in QGIS and geopandas, and all geometries are valid.

## Phase 2 — Landscape, weather and ignition inputs

**Objective:** make every simulation input versioned, aligned and regenerable.

**Tasks**

- **Landscape:** record LANDFIRE version and year, download date, layers, bounding box, native resolution, and the resampling method used to reach 60 m. State the fuel model system. Document canopy and barrier layers.
- **Weather, historical:** document the NSRDB source, location, years, and how the fall and summer periods were selected.
- **Weather, synthetic:** tabulate parameters (temperature, humidity, wind speed and direction, dead fuel moisture), the generator script and the random seed.
- **Wind convention:** define whether N, E, S, W means the direction the wind blows from or toward. The paper uses both senses.
- **FARSITE configuration:** version, 60 m resolution, 30-minute time step, crown fire method, 20% spotting, distance and perimeter resolution. Clarify what 'burn period of 10 hours over 3 days' means.
- **Ignition points:** document how 686 points arose from 702 km at 1 km spacing (per-line rounding?), the time of ignition, and how the 30 m buffer relates to the 60 m cell size.

**Deliverables**

- D2.1 Landscape package (layers plus provenance sheet).
- D2.2 Weather files, generator script and parameter table.
- D2.3 FARSITE input and configuration files.
- D2.4 Ignition points (GeoJSON and CSV): ign\_id, line\_id, chainage\_km, lon, lat.
- D2.5 Inputs documentation including the wind convention.

**Pass criteria**

- P2.1 Every layer has version, source, access date, CRS and resolution recorded.
- P2.2 All raster layers share extent, CRS and cell alignment.
- P2.3 Regenerating the synthetic weather with the recorded seed yields identical checksums.
- P2.4 Ignition count equals 686, the per-line table sums to 686, and it reconciles with the line lengths.
- P2.5 A test fire shows spread direction consistent with the documented wind convention.
- P2.6 The buffer versus cell-size question is resolved and recorded in the decision log.
- P2.7 A full FARSITE run can be launched from the configuration files alone.

## Phase 3 — Simulation reproduction and output archive

**Objective:** rerun all scenarios in a clean, documented environment and archive the outputs.

**Tasks**

- Pin software versions in a container or conda lock file. Run all 4,116 scenarios (686 ignitions × 6 weather conditions).
- Record per-scenario status, runtime and checksum. Capture logs.
- Test determinism on a random sample. Record random seeds if spotting is stochastic.
- Decide the archive scope: final perimeters are mandatory, time-resolved perimeters and arrival-time rasters are optional. Set a size budget.

**Deliverables**

- D3.1 Run manifest (CSV): scenario\_id, ign\_id, line\_id, weather\_id, status, runtime, checksum.
- D3.2 Perimeter archive (GeoPackage or Parquet per weather condition).
- D3.3 Fire-behavior summaries (arrival time, intensity) where produced.
- D3.4 Environment specification and run logs.
- D3.5 Determinism test report.

**Pass criteria**

- P3.1 All 4,116 scenarios have a recorded status. Failures are listed with reasons.
- P3.2 A rerun of at least 5% of scenarios (206 or more) reproduces final perimeter area within 1% and IoU of at least 0.99. If the model is stochastic, report the distribution instead.
- P3.3 Every output file has a checksum in the manifest, and total size fits the chosen repository's limits (confirm the limits).
- P3.4 The environment rebuilds from the specification on a clean machine.
- P3.5 All perimeter geometries are valid and in the declared CRS.

## Phase 4 — Impact analysis, ACOPF and metrics

**Objective:** recompute all metrics from released intermediates and fix the mathematical presentation.

**Tasks**

- Specify the exact spatial rules: a line is affected when it intersects the perimeter, and the node rule must be stated precisely.
- Specify the grid-modification rule and virtual high-cost generator parameters (cost and size). State solver, version, tolerances and voltage limits.
- Compute the affected matrices (A\_ns, A\_js), curtailment (P^o\_jsn), and the susceptibility, risk and vulnerability metrics.
- Write a rule for zero-demand nodes. Equations (12) and (13) divide by node demand, which is undefined at many nodes.
- Fix the notation: define Z, the per-line scenario set Z'\_j and the symbol Z-bar in (11). Correct the line-flow equations (7) and (8), which currently show a nodal injection form.
- Implement unit tests, and compare results to Tables 1–4 of the IEEE Access paper.

**Deliverables**

- D4.1 Impact matrices in long format: scenario\_id, element, affected.
- D4.2 ACOPF results per scenario: solver status, cost, curtailment per node, generator outputs.
- D4.3 Metric tables by weather condition and mean, for lines and nodes.
- D4.4 Metric definition note: exact math, set definitions, zero-demand rule, code mapping.
- D4.5 Test suite and a comparison report against published Tables 1–4.

**Pass criteria**

- P4.1 At least 95% of recomputed table entries match the published values within ±0.001, and every other difference is in the discrepancy log with a cause.
- P4.2 Convergence is reported for every scenario. Non-converged or infeasible cases number zero, or are enumerated with their handling.
- P4.3 Curtailment in every scenario is non-negative and does not exceed total system demand.
- P4.4 The zero-demand rule is applied identically to risk and vulnerability, with denominators stated.
- P4.5 Unit tests on a toy 3-bus example with hand-computed answers pass in CI.
- P4.6 Every symbol in every equation is defined, and (7) and (8) are corrected.
- P4.7 A second person's independent implementation of susceptibility and risk agrees exactly with the main code.

## Phase 5 — Technical validation

**Objective:** produce quantitative evidence that the dataset is sound, and an honest statement of its limits. This is the weakest part of the current work and the one data-descriptor reviewers will weigh most.

**Tasks**

- **Internal consistency:** topology, units, curtailment bounds, scenario coverage per line and weather condition.
- **Sensitivity:** ignition spacing (for example 0.5, 1 and 2 km on a subset), buffer width, wind speed and humidity perturbations, ignition time of day.
- **Convergence:** bootstrap confidence intervals over scenarios, and stability of the top-ranked lines and nodes.
- **Fire-model plausibility:** compare simulated fire against at least one historical fire in or near the region using official perimeters. Candidate: the 2013 Rim Fire (verify that its extent overlaps the study area). Report fit measures such as Jaccard or Sørensen indices.
- **Support for the 'strategic location' claim:** relate metrics to along-line fuel, slope and aspect statistics, since the paper asserts but does not show this link.
- **Limitations:** 2D simulation, no canopy or line height, topology-only electrical mapping, whole-line metrics, synthetic network.

**Deliverables**

- D5.1 Validation scripts and notebooks.
- D5.2 Sensitivity report.
- D5.3 Convergence and rank-stability report.
- D5.4 Historical fire comparison.
- D5.5 Limitations and intended-use statement (benchmark for method comparison, not for operational decisions).

**Pass criteria**

- P5.1 Pass thresholds are set and recorded before analysis. Suggested: top-10 overlap of at least 80% and Spearman rho of at least 0.9 between baseline and sensitivity runs. Any miss is reported and explained.
- P5.2 95% confidence intervals are reported for every published metric, and the top-5 risk lines are stable or the instability is documented.
- P5.3 At least one historical fire is compared quantitatively. Modest fit is reported honestly.
- P5.4 Each stated limitation maps to a usage note for data users.
- P5.5 Every validation figure regenerates from scripts.

## Phase 6 — Packaging, documentation and repository

**Objective:** make the dataset understandable and usable by a stranger.

**Target structure**

```
data/ network, landscape, weather, ignition, simulation, results
src/  notebooks/  tests/  docs/
README.md  CITATION.cff  LICENSE-code  LICENSE-data
CHANGELOG.md  datasheet.md  MANIFEST.csv
```

**Tasks**

- Rewrite the README. Remove all template placeholders (fake BibTeX and DOI, 'Your Name', 'Other Authors – Affiliation', 'a.b.c' and '1.2.3' versions, the 'https://....' link). Use the real article DOI, authors, affiliations and dependency versions.
- Add LICENSE files. The README currently cites an MIT license file that is not in the repository. Use a permissive data license (for example CC BY 4.0 or CC0) and a code license.
- Remove .DS\_Store and other system files, and fix .gitignore.
- Write a data dictionary covering every file and column with units, and a datasheet.
- Write a quickstart notebook: load the network, overlay a perimeter, recompute one metric.
- Set up CI to run the tests. Handle large files via LFS or an external archive.
- Deposit on the chosen repository to mint a DOI, link the GitHub release to it, and use embargo if the provider allows until acceptance.

**Deliverables**

- D6.1 Clean repository tagged v1.0.0.
- D6.2 Data dictionary.
- D6.3 Datasheet.
- D6.4 Quickstart notebook.
- D6.5 DOI-minted deposit.
- D6.6 CITATION.cff and license files.

**Pass criteria**

- P6.1 An automated scan finds no placeholder strings (TODO, 'Your Name', 'a.b.c', '10.12345', 'https://....').
- P6.2 Every file appears in MANIFEST.csv with a checksum, and every column appears in the data dictionary.
- P6.3 License files exist and match the README and deposit metadata.
- P6.4 The independent verifier completes the quickstart from a fresh clone in a clean environment in about an hour, without asking the authors questions.
- P6.5 CI is green.
- P6.6 The DOI resolves, and its metadata (authors, ORCIDs, funding, related identifier to the IEEE Access paper) is complete.
- P6.7 No secrets, system files or absolute local paths remain.

## Phase 7 — Manuscript

**Objective:** a complete, traceable data descriptor that is clearly distinct from the IEEE Access paper.

**Outline**

- Abstract.
- Background and Summary: motivation, gap, comparators, contributions, intended uses.
- Methods: network, landscape, weather, scenarios, simulation, grid modification and ACOPF, metrics with the corrected math.
- Data Records: files, formats, IDs, repository, license.
- Technical Validation.
- Usage Notes: wind convention, link handling, 2D limitation, how to extend.
- Code Availability.
- Funding, author contributions, competing interests (note Quanta and Pyrologix affiliations).

**Planned figures and tables:** workflow, network map, data layers, example scenario overlay, metric maps, validation summary; comparator table, file inventory, weather parameters, FARSITE configuration, validation results.

**Tasks:** write against the venue template, build a provenance sheet mapping each figure and table to its script, verify all references (DOIs resolve, the FARSITE report's year and details, LANDFIRE cited for landscape data, no citation reused for unrelated claims), run a similarity check, redraw or obtain permission for any reused figure.

**Deliverables**

- D7.1 Full manuscript draft.
- D7.2 Figure and table provenance sheet.
- D7.3 Verified reference list.
- D7.4 Similarity report with explanation of overlap.
- D7.5 Internal review comments and resolutions.

**Pass criteria**

- P7.1 All required sections are complete per the target venue's template.
- P7.2 Every number and figure traces to a script path.
- P7.3 Every claim in Background is supported by a citation, and every reference is verified.
- P7.4 Equations match D4.4, and limitations match D5.5.
- P7.5 Text overlap with the IEEE Access paper is confined to cited methods and explained.
- P7.6 The data availability statement matches the DOI and license.
- P7.7 At least two internal reviewers (one fire scientist, one power-systems researcher) have reviewed it and all comments are resolved.
- P7.8 CRediT, funding and competing-interest statements are complete.

## Phase 8 — Final verification, submission and maintenance

**Objective:** prove reproducibility from scratch, submit, and plan for upkeep.

**Tasks**

- Cold-start reproduction by a person outside the build team using only the documentation and the DOI deposit. File and fix every issue they hit.
- Freeze v1.0.0, prepare the submission package and cover letter, and identify suggested reviewers.
- Handle review rounds with a response log. If recomputation (Phase 4) found material errors in the published paper, discuss a correction notice with the journal.
- After acceptance: make the deposit public, update README and CITATION.cff with the final article DOI, and announce it.
- Define the maintenance plan: issue tracker, versioning policy, bug-fix process, response times.

**Deliverables**

- D8.1 Signed reproduction report.
- D8.2 Submission package and cover letter.
- D8.3 Response-to-reviewers log (if applicable).
- D8.4 Maintenance plan and v1.0.0 release.

**Pass criteria**

- P8.1 The cold-start reproduction reaches the core results using only the documentation, with all issues fixed or logged.
- P8.2 Gate sign-offs for Phases 0–7 are on file.
- P8.3 The submission passes the journal's technical check without format-related return.
- P8.4 After acceptance, the DOI is public and the README cites the final article.
- P8.5 The maintenance plan names an owner and response times.

## 5. Key risks and mitigations

- **Output archive too large:** release final perimeters only, make time-resolved outputs optional, compress, and use an external archive for the bulk.
- **FARSITE runs not reproducible:** pin versions and seeds, and report a tolerance or distribution.
- **Recomputed metrics differ from the paper:** treat as a finding, log the cause, and decide on a correction with the journal if material.
- **Reviewers question novelty against CATS and similar systems:** lead with the bundled scenarios, outputs and reproducible pipeline, backed by strong validation.
- **Weak calibration against historical fires:** report honestly and position the dataset as a benchmark, not a predictive model.
- **Rights or license conflicts:** resolve in Phase 0, before any release work.
- **Scope creep:** enforce the scope freeze and keep extensions in the v1.1 backlog.
